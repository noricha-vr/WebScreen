# 画質の設計（実測 2026-08-29 / 安定性再検証 2026-09-01）

> **採用設定は入力 1280x720 / 30 fps / 映像上限 1200 kbps / `detail` / `maintain-resolution` / scale 1 の単一設定。**
> 本番relayの合成motion/static QAは、動画像で1280x720・30 fps・total egress約1.04 Mbps・freeze 0を確認した。WebScreen UIからのactual YouTube最終確認は未実施。
> 最新の設定・同条件比較・再接続方針は [stability-audio-verification.md](stability-audio-verification.md) を正本とする。
> 以下の 300〜1500 kbps の表は過去の判断経緯として残すが、現行実装値ではない。

**「より多くの人に配信する」ための画質設計。** 収容人数の計算は [capacity.md](capacity.md)、実装設定は [requirements.md](requirements.md)。

## 結論

旧設計では解像度を守って fps を削ったが、ライブの主用途を動画・動く画面へ絞ると、fps 低下そのものが不具合になる。
既存比較では 30 fps を優先し、24 fps も 1.1〜1.3 Mbps で比較したが、RTSP 出口がすべて 23 fps 未満だったため採用しない。
旧 `maintain-framerate` 測定では入力 1280x720 に対し実送出が 960x540 になった。採用設定はI18で動画像の1280x720・30 fps・freeze 0、
16 / 24 px文字の明瞭さと12 pxの判読性を確認した。WebScreen UIからのactual YouTube最終確認までは、入力要求と実送出解像度を区別する。

| 段 | 上限指定 | **実効ビットレート** | **実 fps** | 解像度 | 12px 日本語 | 用途 |
|---|---|---|---|---|---|---|
| **省帯域** | 300 kbps | **267 kbps** | **1.7 fps** | 1920x1080 | **読める** | 資料・スライド・静的なページの共有 |
| **標準（既定）** | 600 kbps | **352 kbps** | **24.5 fps** | 1920x1080 | **読める** | 通常。スクロールも自然に見える |
| なめらか | 2000 kbps | 613 kbps | 30.0 fps | 1920x1080 | 読める | 動きの多いページ。**費用対効果は低い** |

すべてスクロール中（120 px/秒）の実測。静止しているページでは実効値がさらに下がる（600 kbps 指定で 103〜164 kbps）。

## 初版からの訂正

初版は実効 **633 kbps** を標準としていたが、これは上限を 2000 kbps に置いた（実質無制限の）測定値だった。
**上限を 600 kbps に設定すると実効 352 kbps・24.5 fps** になり、**帯域が 44% 減って fps は 30→24.5 しか落ちない**。
初版の 633 kbps は 1.8 倍の過剰だった。

## なぜ fps が削れるのか

`maintain-resolution` は「解像度を守り、足りなければフレームを落とす」という指定。
静止したテキストページを見せる用途では**この振る舞いが正しい**:

- 文字が潰れるとサービスの意味がなくなる（読むための道具なので）
- スクロールが多少かくついても、読むこと自体は妨げられない

逆に既定のまま（`motion` + `maintain-framerate`）にすると、300 kbps では **640x360 まで解像度が落ちて文字が完全に判読不能**になる。
QP は既定寄りの方が良い（19.6 vs 35）にもかかわらず読めない。**「圧縮を緩める」ではなく「解像度を守る」が正しい操作。**

## 段を下げると何人増えるか

制約は 3 つあり、**どれが効くかはサーバーによって変わる**。

| 段 | 実効 | 帯域あたり | CPU あたり（実測） | 転送量あたり |
|---|---|---|---|---|
| 省帯域 267 kbps | 1.00x | **2.3 倍** | **1.8 倍**（0.158%/reader） | **1.3 倍** |
| 標準 352 kbps | 1.32x | 1.7 倍 | 1.0 倍（0.291%/reader） | 1.0 倍 |
| なめらか 613 kbps | 2.29x | 1.0 倍 | 0.6 倍（外挿） | 0.6 倍 |

（標準を 1.0 とした時の収容人数の比）

**省帯域に落とす効果は「2 倍強」であって「桁が変わる」ものではない。** 一方 fps は 24.5 → 1.7 と体感で大きく変わるので、
**既定を省帯域にはしない**。ユーザーが選べるオプションとして置く。

## fps を下げることそれ自体には意味がない

実測で確認した重要な性質: **サーバーの CPU はフレーム数ではなくバイト量に比例する。**

| 条件（600 kbps 固定・reader 20 本） | CPU/reader |
|---|---|
| 1080p **30 fps** | 0.185% |
| 1080p **15 fps** | 0.195% |
| 1080p **5 fps** | 0.205% |

同じビットレートなら fps を 6 分の 1 にしても CPU は下がらない（むしろ誤差程度に増える）。
**「fps を下げて軽くする」という設計は無効**で、効くのはビットレートだけ。
ただし fps を下げると同じ画質をより低いビットレートで作れるため、**ビットレート上限を下げる手段としては有効**。

## 480p を作らない理由

解像度を下げる方向は**この設計では不要**。`maintain-resolution` が 1080p を守るため、帯域が足りなければ自動で fps 側が落ちる。
480p まで落とすと 14px 以下が判読不能になり、**帯域を足しても直らない**（解像度不足は後から取り戻せない）。

## 実装への反映

```ts
const parameters = sender.getParameters();
parameters.encodings = parameters.encodings?.length ? parameters.encodings : [{}];
parameters.encodings[0]!.maxBitrate = 1_200_000;
parameters.encodings[0]!.scaleResolutionDownBy = 1;
parameters.degradationPreference = 'maintain-resolution';
await sender.setParameters(parameters);
track.contentHint = 'detail';
```

画質モードの UI は作らず、全配信でこの単一設定を使う。

full設定がブラウザに拒否された時はfresh parametersからmaxBitrate-only fallbackを1回だけ試す。これは配信継続の互換策であり、文字品質を保証しない。

## 実機検証を受けた段構成（2026-09-01 確定。Issue #124）

VRChat 実機の実測（verification.md I5 / I7 / I8）で分かったこと:

1. **600 kbps は動画素材で破綻する**: YouTube 再生中の画面共有はデルタフレームが実質空になり、
   表示がキーフレーム周期（2 秒）でしか進まない = 約 3 秒 1 枚のコマ送り + **体感遅延が 0.5〜2.5 秒に揺れる**
2. **2500 kbps なら動画素材でも約 26 fps・遅延 0.08 秒**（実効 1.5 Mbps）
3. **ビットレート不足は「画質の問題」ではなく「遅延と更新頻度の問題」として現れる**（解像度は落ちないため文字は読める）
4. サーバー CPU は律速でない（I8）ため、段を増やすコストは帯域・転送量のみ

MP3 betaの500 msキーフレーム要求は画質段ではなく、Chrome限定の途中参加回復候補である。単純な720p30合成シーンでは237→456 kbpsへ増えたため、通常AACへ一律適用せず `stream-profile=mp3-beta` の明示時だけ有効にする。24 fpsのheadless合成測定は20.5 fpsへunder-deliveryしたため判断に使わず、実Macの10分比較で30 fpsを採用した（[verification.md](verification.md) I22）。

### 旧決定: 段を作らず 1500 kbps 単一（2026-09-01・Issue #124）

この判断は同日の YouTube 再生でカクつきが出たため、いったん **上限 2000 kbps / 30 fps / motion 優先へ上書きした**。
その後の 30 / 24 fps・1.1〜1.3 Mbps 再検証により、現行は 720p入力 / 30 fps / 1200 kbps へ更新した。
画質モードの選択 UI を作らない方針は維持する。

| 項目 | 値 |
|---|---|
| maxBitrate | **1500 kbps（単一）** |
| 実効（実ページのスクロール中） | 約 1,620 kbps |
| 実効（静止時） | 100〜160 kbps（内容駆動で自動的に下がる） |
| Indigo 8GB の同時視聴目安 | 約 432 人（帯域律速） |

#### なぜ段を作らないのか

**1. 静止資料はライブ配信の仕事ではない。** PDF・スライド・画像は既存の変換機能（MP4 → CDN 配信）で配れる。
そちらは視聴者数が帯域を消費せず、VRChat の allowlist も既存ドメインで済む。
ライブ配信が担うのは「リアルタイム性そのものに価値がある用途」だけなので、
資料向けの省帯域段（300k）は用途ごと存在しない。

**2. 上限は「天井」であって常時消費ではない。** `maintain-resolution` + `contentHint: 'text'` の下では
実効ビットレートは内容駆動で決まり、静止したページなら 1500k 指定でも 100〜160 kbps しか流れない。
段を分けても静止時の転送量は変わらず、**分岐が増える割に得るものがない**。

**3. 1200k 以上は体感が飽和する。** 実ページ素材のスイープ（下表）で 1200k から fps が頭打ちになり、
VRChat 実機でも 1200k / 1500k / 2000k の差を体感できなかった（2026-09-01・ProTV）。
実測の膝は 1200k だが、**うねり・ちらつきの余裕**を持たせて 1500k を採る
（VRChat 向け配信の事実上の標準 TopazChat の推奨値と同値。出典:
[TopazChat 公式 README](https://github.com/TopazChat/TopazChat) 参照日 2026-09-01）。

#### 実ページ素材のレートスイープ（2026-09-01 実測）

画像込みの実 Web ページを 240 px/秒で往復スクロールさせ、Indigo 経由の RTSP 出口で測定。
`freezedetect` は 0.4 秒以上の停止を検出した合計秒数（20 秒窓）。

| 上限 | 受信 fps | フリーズ合計 | 実効 |
|---|---|---|---|
| 600 kbps | 8.7 | **2.3 秒** | 533 kbps |
| 800 kbps | 14.3 | 0.7 秒 | 819 kbps |
| 1000 kbps | 20.6 | 0.5 秒 | 1,052 kbps |
| 1200 kbps | 24.9 | 0 | 1,273 kbps |
| **1500 kbps** | **24.8** | **0** | **1,618 kbps** |
| 2000 kbps | 25.9 | 0 | 2,118 kbps |

**当初の標準 600 kbps は実ページでは破綻していた**（20 秒中 2.3 秒フリーズ）。
本ファイル上部の段表（文字ラダーの合成素材で 24.5 fps）は素材が軽すぎたための過大評価で、
実ページでは 2 倍の帯域が要る。

#### 却下した代替

- **3 段（省帯域 300k / 標準 600k / 動画 2000k）**: 静止資料は変換機能の領分で省帯域段の用途がなく、
  600k は実ページで破綻する。動画段だけ残すなら単一と変わらない
- **2 段（ページ 1200k / 動画 1500k）**: 差が 300k しかなく、実機で体感差もない。
  分岐のコスト（UI・文言・検証マトリクス）に見合わない
- **一律 2000 kbps**: 収容が 330 人まで落ちる。実機で 1500k との差を体感できなかったため余剰

#### 旧判断時の将来モード追加条件

次のいずれかが実測で確認できたら、その時に段を追加する（**先回りして作らない**）:

- 大人数イベント（同時 400 人超）の主催者から収容確保の要望が出た → 低レート段
- 1500k で破綻する素材（高フレームレートのゲーム画面等）の報告が出た → 高レート段

### 旧判断時の訴求と UI の要件

- 当時の遅延訴求は「対応ワールド（Use Low Latency ON）なら 0.1 秒級」（I7）。
  1500k 単一で素材によらず成立すると判断したが、その後 YouTube 再生でカクついたため一度 2 Mbps に上書きした
- 画質モードの選択 UI は作らない。静止資料の共有は既存の変換機能へ誘導する（実装 #128）
- **発行する配信 URL の path にハイフンを含めない**（#93 の 12 文字英小文字+数字の規則を厳守）。
  2026-09-01 の実機テストで、ハイフン入りの path を VRChat に貼るとハイフン以降が欠落し
  「映らない」状態になる事例を確認した（サーバーログに切り詰められた path への接続が残る）

## 1.2 Mbps 採用設定で残る最終確認
